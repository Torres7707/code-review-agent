1 项目定位与范围

✅ 项目目的

个人作品：自动化扫描 GitHub PR 中的 React 代码问题， 让开发者在合并代码前快速发现 bug、hook 误用、性能和安全缺陷。

👤 目标用户

个人使用（当前阶段）：单用户登录，保存在本地浏览器，不涉及数据库和多用户隔离。

🎯 3 个核心价值

  1. 零摩擦：不用复制代码，点 PR 就行
  2. 结构化：不是给你一段 markdown，而是带严重度和修复建议的 Issue Cards
  3. 流式响应：结论逐字出现，不用等，感知速度快

🚫 明确不做（当前阶段）

  • 不做多用户系统、不做数据库、不做权限隔离
  • 不做 Bot 评论回 PR（开 GitHub App 才需要）
  • 不主动监听 Webhook 触发自动审查（需托管后台，Phase 3 再说）
  • 不做 CRUD 历史记录（localStorage 可支持，稍后再加）

4 GitHub OAuth 单用户方案

🔐 实际方案：OAuth App 授权码流（不是 Device Flow）

设计阶段推荐过 Device Flow，实现时改成了标准 OAuth App 授权码流。原因： 个人项目在浏览器里用，没有"无浏览器设备"的场景；Device Flow 多一步 user_code 输入，还要在 OAuth App 里单独留意 device flow 开关，而授权码流 在 localhost 和 Vercel 上都只需要登记一个 callback URL。刷新页面无需重登录。 

// 流程（已实现）
1. 点 "Sign in with GitHub" → GET /api/auth/github
2. 生成随机 state，写入 cra_oauth_state cookie（10 分钟，HttpOnly）
3. 302 跳转 github.com/login/oauth/authorize
   ?client_id=...&scope=repo read:user&state=...
4. 用户授权后 GitHub 回调 /api/auth/callback?code=...&state=...
5. 后端比对 cookie 中的 state 与查询参数，不一致直接拒绝
6. POST github.com/login/oauth/access_token，用 code 换 access_token
7. HMAC-SHA256 签名 token → Set-Cookie: cra_session=<base64url>.<mac>
   HttpOnly; SameSite=Lax; Max-Age=30天（生产环境额外加 Secure）
8. 无 middleware：需要 token 的 route handler 各自 readSession(req)，
   验签通过返回 token，失败返回 null（不区分"过期"与"伪造"）

📁 代码结构（已实现）

  • 不适用于多用户

5 GitHub REST API 调用设计

📦 需要调用的接口

方法 / 路径 用途 返回内容
GET /user 获取当前登录用户 login, avatar, name
GET /user/repos 拉取所有仓库 [{ name, full_name, stargazers_count }]
GET /repos/:owner/:repo/pulls PR列表（open状态） [{ number, title, user.login, ... }]
GET /repos/:owner/:repo/pulls/:pr/files PR所有变更文件 [{ filename, patch, ... }]
GET /repos/:owner/:repo/pulls/:pr PR 详情 / diff_url { body, diff_url, ... }

🔧 核心代码示例

// lib/github.ts
export async function fetchRepoFiles(repo: string, pr: number): Promise<File[]> {
  const token = getAuthToken(); // 从 cookie 解密
  const res = await fetch(
    `https://api.github.com/repos/${repo}/pulls/${pr}/files`,
    {
      headers: {
        Authorization: `Bearer ${token}`,
        Accept: 'application/vnd.github+json',
      },
    }
  );
  if (!res.ok) throw new Error(await res.text());
  return res.json();
}

// 后端拼接 patch 成 diff 文本
const diffText = files.map(f => f.patch).join('\n\n---\n\n');
// 然后传给 streamText() 做流式审查

⚠️ GitHub API 限额

  • 未认证: 60 次/小时（够用，单用户）
  • 认证后: 5000 次/小时（足够）
  • 大 PR（超过 3000 行 / 100+ files）用 files 接口会截断，需要个 cursor 分页
  • 建议加响应时间：GitHub API 通常 100-500ms

🔥 核心 Prompt 修改（已落地）

旧 Prompt 让模型输出 markdown 正文（🔴/🟡/🟢 分节），这与结构化输出冲突， 已改写为与 reviewSchema 一致的对象描述。注意：是否真是 JSON 由 Output.object 约束，Prompt 不再要求"只返回 JSON"， 只描述每个字段该写什么——两处同时强制反而容易让模型把 JSON 包进代码块。 

// lib/review-schema.ts — 服务端与客户端共用的唯一来源
export const reviewIssueSchema = z.object({
  severity: z.enum(["high", "medium", "low"]),
  title: z.string(),
  file: z.string(),
  startLine: z.number().int(),
  endLine: z.number().int().optional(),
  why: z.string(),
  fix: z.string(),
});
export const reviewSchema = z.object({
  summary: z.string(),
  issues: z.array(reviewIssueSchema),
});

// app/api/review/route.ts
const result = streamText({
  model: process.env.AI_MODEL ?? "openai/gpt-5-mini",
  instructions: REVIEW_PROMPT,
  prompt: buildReviewPrompt(body),
  abortSignal: req.signal,
  output: Output.object({ schema: reviewSchema }),
});
return result.toTextStreamResponse();
